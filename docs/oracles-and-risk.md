## Дев’ять інструментів і ризик

| Клас | Інструменти | Наслідок помилки / спосіб контролю |
|---|---|---|
| Read | get_account,get_transactions,check_limits,search_knowledge_base | Неправильний контекст для наступного рішення; перевірка по trace |
| Compute | quote_fx,check_dispute_eligibility | Неправильний висновок без write; порівняння з доменним кодом/контрактом |
| Write зворотний | escalate_to_human | Зайва/пропущена черга; ручна корекція оператора, у suite цього ДЗ окремо не перевірено |
| Write незворотний | create_dispute,send_statement | Зовнішній процес спору або фінансові дані стороні; бар’єр до виконання й перевірка постстану |

Це доменна класифікація лекції. Локальний send_statement фактично лише вставляє рядок,
SMTP у ньому немає; rollback тестової БД не доводить зворотність зовнішньої дії.

## Запропоновані бар’єри перед незворотними діями

| Інструмент | Перевірка до виконання | Ціна затримки | Легітимний сценарій, який постраждає |
|---|---|---|---|
| create_dispute | Доменна eligible-перевірка; account/currency з transaction_id; idempotency | Оцінка +2–10 мс: 2 локальні DB читання (transaction/customer, наявний спір), 1 виклик disputes engine; без LLM/network round-trip | Помилка доменних правил може відхилити дозволений спір; розгляд винятку потребує оператора |
| send_statement | Звірка власника рахунку й verified email незалежно від моделі | Оцінка +1–5 мс: 1 DB join власника/verified email і звірка в коді; нова адреса — окреме очікування підтвердження | Клієнт просить надіслати на іншу законну робочу пошту |

Рішення про write не делегувати лише model prompt. Застосування цих бар’єрів не заявляється як реалізоване виправлення.
D10 scripted-guard і тест повтору send_statement лишаються опційними: основний suite не покриває ідемпотентність кожного write.

## Опис і результат як специфікація

Фактичні9 input schemas/description та відмінності D13 знімаються environment-тестом у tool-contracts.json.
Склад інструментів та їхні типи не вигадуються з trace відповіді.
D29 контракт: eligible:boolean,checks:object; у D29 поле ok не заміняє eligible.
Native tool_result_schema — перевірка названих полів і Python-типів, не повна JSON Schema/MCP-реалізація.
Кіт може вважати bool числом у number-перевірці; цей suite числову output-schema цим механізмом не валідовує.

ToolCorrectnessMetric описується лише як межа: без нашого state/trace/cache вона не заміняє ці перевірки.
Порівняння з актуальною версією бібліотеки — опційне, тут не виконувалося.

## Підготовка й ціна

Історію відтворює MockServer; інструменти на мок-кроках справжні. Лише останній live-крок оцінюється.
Природа assertions визначає daily/release; runs5 у daily заборонено.
Повні52 live-кроки; пілот6 окремо; прогноз вартості лише після пілота.
Змішана мова/змінний префікс/порядок tools можуть зламати кеш без D28.
Діалоги коротші summarize_after8; summary не повинна відбуватися.

Непокрито: потреба клієнта поза формальним проханням, відновлення state у production, privacy/IDOR,
повноцінний MCP-сервер, відправка справжнього email, latency benchmark. Це явні межі, не PASS.

Оцінки додаткової затримки припускають прогріту локальну БД без contention. Це бюджет запропонованих бар’єрів, не вимірювання чинного tool. Підтвердження нової адреси людиною до мілісекундного бюджету не входить.
